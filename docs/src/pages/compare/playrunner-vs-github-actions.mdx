# Playrunner vs GitHub Actions

Nobody sets out to build an internal test platform. It accumulates. A workflow
file gets a matrix, then a schedule, then a retry block, then a step that posts
to Slack, then a step that opens a Jira ticket, then a conditional that skips
all of it on draft PRs. A year later the browser-testing pipeline is a thousand
lines of YAML and two team-owned scripts, and exactly one person understands the
retry semantics.

**Playrunner is not replacing GitHub Actions. It is replacing the orchestration
glue you piled on top of it.**

## The honest split

GitHub Actions is very good at what it was built for: reacting to repository
events, gating merges, and deciding what is allowed to ship. None of that moves.

What tends to fit badly is everything downstream of "the tests failed" — the
branching, the notifications, the ticket creation, the artefact routing, the
environment matrix, the schedule that is unrelated to any commit.

|                                      | GitHub Actions                                              | Playrunner                                                                              |
| ------------------------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Reacting to pushes and pull requests | Native                                                      | Not its job — trigger Playrunner from CI                                                |
| Gating merges and deployments        | Native                                                      | Not its job                                                                             |
| Where the browser actually runs      | A GitHub-hosted or self-hosted runner you configure per job | A runner you select on the node: local Docker, managed cloud, or your own cloud account |
| Conditional branching after a run    | `if:` expressions across steps and jobs                     | An edge on the canvas, drawn between two nodes                                          |
| Notifications and ticket creation    | A marketplace action plus its config per workflow           | A node, configured once, reusable across workflows                                      |
| Scheduled runs                       | `on: schedule` cron per workflow file                       | A Schedule node, visible on the canvas                                                  |
| Seeing what a run actually did       | Log scrollback per job                                      | Live node state and logs on the graph, with artefacts attached to the run               |
| Changing the flow                    | Edit YAML, push, wait for a run to find out                 | Move a connection, save                                                                 |

## What this looks like in practice

A typical "mature" Playwright job in GitHub Actions carries a browser matrix, a
shard strategy, a cache step, an artefact upload, a conditional Slack post, a
conditional issue-creation step, and a nightly `schedule` twin that duplicates
most of it because the trigger differs.

In Playrunner that is one graph: a trigger node, an environment node, a
Playwright node, and edges out of it — a failure edge into triage, a success
edge into whatever comes next. The condition lives on the connection rather
than inside a script, so reading the flow does not require reading YAML.

The tests themselves are untouched. Playrunner connects to the repository and
runs the specs and configuration you already maintain.

## Using both together

The common end state is not "we left GitHub Actions". It is:

1. GitHub Actions still runs on pull requests and still gates the merge.
2. The heavy browser-testing workflow moves to Playrunner.
3. CI calls Playrunner when it needs a verdict:

```yaml
- name: Run the Playrunner quality gate
  run: npx --yes playrunner ${{ vars.PLAYRUNNER_WORKFLOW_ID }} \
    --url ${{ vars.PLAYRUNNER_URL }} \
    --timeout 30m
  env:
    PLAYRUNNER_API_KEY: ${{ secrets.PLAYRUNNER_API_KEY }}
```

The CLI exits non-zero when the workflow fails, so it gates exactly like any
other step. See [the CI/CD quality gate post](/blog/playrunner-ci-cd-pipeline/)
for the full setup.

## When GitHub Actions alone is the right answer

Be honest about this — if the following describes you, you do not need
Playrunner yet:

- Your Playwright job is one straightforward workflow file that nobody dreads
  editing.
- Tests only ever run on push or pull request, and the result only ever needs
  to pass or fail.
- Nothing happens after a failure except a red check.
- You have no scheduled runs, no environment matrix, and no downstream systems
  to notify.

Playrunner earns its place when the _surrounding_ workflow has grown past what
YAML expresses comfortably — not simply because you run Playwright in CI.
