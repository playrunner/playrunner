# Playrunner vs Azure Playwright Workspaces

:::note Verify before you budget
Microsoft's testing products moved twice in a year. Everything below reflects
Microsoft's published documentation at the time of writing, but check the
[Azure App Testing product page](https://azure.microsoft.com/en-us/products/app-testing)
and [pricing page](https://azure.microsoft.com/en-us/pricing/details/app-testing/)
before making a decision — the details move faster than comparison pages do.
:::

## What actually changed

Microsoft Playwright Testing ran as a preview service and was **retired on 8
March 2026**. Its capability was folded into **Azure App Testing**, a unified
service that also contains Azure Load Testing, where the Playwright side is now
generally available as **Playwright Workspaces**.

If you were on the preview, the migration path is to create a new Playwright
Workspace in Azure App Testing. Playwright itself is untouched — this was a
change to Microsoft's managed service, not to the framework.

## What Playwright Workspaces gives you

Credit where it is due. This is a solid managed grid:

- **Cloud-hosted browsers** across Chromium, WebKit, and Firefox.
- **Parallel execution** at scale — Microsoft documents up to 100 parallel
  tests, across multiple regions.
- **Reporting**, accessible through the Azure portal, with bring-your-own
  storage for artefacts, configurable retention, and shareable report URLs.
- **Per-second billing** on a published per-test-minute rate.
- **Azure-native identity, governance, and compliance**, which for an
  Azure-committed organisation is a genuine and hard-to-replicate advantage.

If what you need is "more browsers, faster, without managing the fleet", that
is exactly what it does.

## What it leaves you to build

Playwright Workspaces is positioned as test execution and reporting. Microsoft
does not document it as a workflow product, and it is not one. Nothing in it
answers:

- **What starts a run** beyond your CI invoking it — no schedules, no inbound
  webhooks as a first-class trigger.
- **What happens after a run** — no conditional branching on the outcome, no
  Slack or Jira or email step, no downstream deploy trigger.
- **How environments are wired** across a family of related runs.
- **Whether a second workflow should follow the first**, and only on success.

Those gaps get filled the way they always do: in CI YAML and a couple of
team-owned scripts.

## Side by side

|                                      | Azure Playwright Workspaces                      | Playrunner                                              |
| ------------------------------------ | ------------------------------------------------ | ------------------------------------------------------- |
| Cloud browsers, managed and parallel | Yes — the core of the product                    | Provisions runners; does not sell browser minutes       |
| Test reporting and artefacts         | Yes, in the Azure portal, bring-your-own storage | Yes, attached to the run, with live node state          |
| Scheduled runs                       | Not a documented feature                         | Schedule node                                           |
| Webhook triggers                     | Not a documented feature                         | Webhooks node, inbound and outbound                     |
| Conditional branching on outcome     | Not a documented feature                         | An edge on the canvas                                   |
| Slack, Jira, email, AI triage        | Not a documented feature                         | Integration nodes                                       |
| Runs on your own infrastructure      | Azure-hosted                                     | Local Docker, managed cloud, or your own cloud account  |
| Pricing model                        | Per test minute, per second billing              | Free to self-host; hosted Cloud in beta                 |
| Best when                            | You are Azure-committed and want a managed grid  | The workflow around the run is what you are maintaining |

## The two are not mutually exclusive

The honest framing: **a grid answers "where does the browser run". Playrunner
answers "when does this run, on what, and what happens next".**

An Azure-committed team can reasonably keep Playwright Workspaces for browser
capacity and use Playrunner for the orchestration, rather than rebuilding the
schedule-and-notify layer in pipeline YAML for a third time.

## Choose Playwright Workspaces if

- Your organisation is committed to Azure and values keeping identity,
  networking, and compliance inside it.
- Your primary problem is browser capacity and wall-clock run time.
- Your CI already handles everything before and after the run, and you are
  happy with that arrangement.

## Choose Playrunner if

- The maintenance burden is the _surrounding_ workflow, not the browsers.
- You want triggers, branching, and integrations to be visible rather than
  distributed across YAML files and scripts.
- You need to run on your own infrastructure, or across more than one cloud.
- You want to start without a cloud commitment — self-hosting is free today,
  with no license fee for permitted use.
