# No-code Playwright orchestration

**Your Playwright tests stay code. The orchestration around them doesn't have
to be.**

That distinction matters, because "no-code testing" usually means something
else entirely — a record-and-replay tool that generates brittle scripts you did
not write and cannot review. That is not this. Playrunner never touches your
specs. It runs the suite you already maintain, and removes the code you never
wanted to maintain in the first place: the pipeline YAML, the notification
scripts, the retry wrapper, the cron job nobody remembers configuring.

If you have used n8n or Prismatic, you already know how to build a Playrunner
workflow.

## What becomes no-code

These stop being code and become nodes and connections on a canvas:

- **Triggers** — a schedule, an inbound webhook, or an API call.
- **Environments** — reusable variables injected into runs, defined once.
- **Branching** — what happens on failure versus success, as an edge between
  two nodes rather than an `if:` expression.
- **Runner selection** — local Docker, managed cloud runners, or your own
  cloud account, chosen on the node.
- **Credentials** — connected once through OAuth, reused across workflows.
- **Downstream systems** — Slack, Jira, email, webhooks, and AI failure
  analysis, as steps in the graph.
- **Reporting** — Playwright reports, traces, and artefacts attach themselves
  to the run.

## What stays code

Deliberately:

- **Your Playwright specs.** Written by engineers, reviewed in pull requests,
  versioned in your repository. Playrunner reads them; it does not generate or
  rewrite them.
- **Your `playwright.config.ts`.** Projects, timeouts, reporters, and fixtures
  all keep working exactly as they do now.
- **Your page objects and helpers.** Untouched.

This is the split that makes the model workable for a team that takes testing
seriously. Test logic belongs in code review. Deciding that the nightly
regression run should post to `#qa-alerts` does not.

## Why the orchestration is the part worth removing

A Playwright suite is usually the healthy part of the system. The unhealthy
part is what grew around it: a workflow file with a matrix and three
conditionals, a shell script that formats a Slack message, a second workflow
that is a copy of the first with a different trigger, and a retry policy that
exists in two places and disagrees with itself.

None of that is test logic. All of it is operational plumbing that happens to
be expressed in code because there was nowhere else to put it. Moving it onto a
canvas does not make the system less rigorous — it makes the actual behaviour
visible to everyone who depends on it.

## What you still need engineers for

Being straight about the limits:

- Writing and maintaining the Playwright tests.
- Deciding what a good test suite covers.
- Debugging a genuinely broken application.

Playrunner reduces the operational surface around testing. It does not replace
the people who write the tests, and it does not pretend that browser automation
stops needing engineering judgement.
